# Plan: Result Caching Implementation

## Objective
Implement a persistent caching layer for OCR results to avoid redundant API calls and processing, significantly speeding up development and re-runs.

## Context
OCR processing is slow (5-10s per image) and sometimes costly (API fees). During development or when re-running batch reports, processing the same unchanged image files is wasteful.

## Requirements
1. **Persistence**: Cache must survive process restarts (file-based or SQLite).
2. **Keying**: Cache key should be based on file content hash (MD5/SHA256) + configuration hash (to invalidate if OCR logic changes).
3. **Transparency**: `BatchProcessor` should check cache transparently.
4. **Invalidation**: CLI flag `--no-cache` to force re-processing.

## Technical Details

**Schema:**
```sql
CREATE TABLE results (
    file_hash TEXT PRIMARY KEY,
    config_hash TEXT,
    data_json TEXT,
    timestamp REAL
);
```

**Hashing:**
- File hash: `hashlib.sha256(open(path, 'rb').read()).hexdigest()` (computed once per file).
- Config hash: Hardcoded version string for now (e.g. "v1.3.0").

## Constraints
- Cache size management (optional for v1, but good to keep in mind).
- Thread safety (SQLite is thread-safe for concurrent reads/writes if managed correctly).
